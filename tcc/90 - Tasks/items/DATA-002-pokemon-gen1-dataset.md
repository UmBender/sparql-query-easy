# Add a built-in first-generation Pokémon dataset for trying the tool

## Objective

The football dataset is a poor playground: few numeric values to filter, and
little that relates in interesting ways. Add a second, small, richly related
built-in dataset with the 151 Kanto Pokémon (National Pokédex #001–#151) so
users can try relations, numeric filters, type weaknesses, evolution lines and
Pokédex history.

Expected examples once done (endpoint field set to `PokemonGen1`):

- Pokémon with `speed > 100`, or with base stat total between 400 and 500.
- Every Pokémon weak to Water; the types that are super effective against Fire.
- Charmander → Charmeleon → Charizard, with the level each evolution happens.
- The Pokémon right after #025 Pikachu in the Pokédex, or every "Seed Pokémon".

## Human decisions (2026-10-05)

- **Access:** a built-in endpoint identifier, typed in the SPARQL Endpoint
  field like `CampeonatoBrasileiro2023`. Additive; not upload-only.
- **Data era:** current games. Today's typing for the 151 species (e.g.
  Clefairy is Fairy, Magnemite is Electric/Steel), six base stats, and the
  current 18-type effectiveness chart.
- **Branch:** implement on its own task branch/worktree so other work can go on
  in parallel on `main`.

## Scope

1. **Dataset** `src/main/resources/pokemon_gen1.ttl`, generated by a committed,
   deterministic, offline script (`scripts/generate-pokemon-dataset.mjs`, with
   the source tables inside it) so the data is reviewable and reproducible.
   Its own namespace (not the football one), with an `rdfs:label` on every
   resource and property so local search and the graph show readable names.
   - `Pokemon` (151): Pokédex number (`xsd:integer`), name, category (e.g.
     "Seed Pokémon"), height (m) and weight (kg) as `xsd:decimal`; HP, Attack,
     Defense, Sp. Atk, Sp. Def, Speed and base stat total as `xsd:integer`;
     links to a primary type and an optional secondary type.
   - **Pokédex history:** links to the next and previous Pokémon by number.
   - **Evolution:** evolves-from / evolves-to links, evolution stage
     (1–3, `xsd:integer`), and how the evolution happens (level with the level
     number, stone with the stone item, trade, or friendship). Branching lines
     (Eevee) and single-stage Pokémon are represented.
   - `Type` (18): super effective / not very effective / no effect against
     other types, following the current chart.
   - Weaknesses per Pokémon, computed by the script from its type(s): weak to,
     resistant to and immune to. A 4× weakness is recorded, e.g. as its own
     property or a multiplier value.
   - No verbatim in-game Pokédex flavor text.
2. **Endpoint** `PokemonGen1`, resolved to its own eagerly parsed,
   process-lifetime graph through the existing built-in boundary, without Jena
   types leaking out of RDF infrastructure.
3. **Tests, docs and packaging** as listed under Validation, plus the canonical
   documentation updates.

## Exclusions

- No change to `futebol_completo.ttl` bytes, its SHA-256, the
  `CampeonatoBrasileiro2023` behavior, the default endpoint value in
  `index2.html`, or C# compatibility captures.
- No dataset picker UI, no other generations, no images or sprites.
- No calls to PokéAPI or other live services at build or test time.

## Acceptance criteria

- `PokemonGen1` resolves to a local, non-Wikidata built-in context; the
  football identifier still resolves to the unchanged football graph.
- SPARQL over the dataset returns, for example:
  - exactly 151 Pokémon with Pokédex numbers 1–151, and 18 types;
  - Bulbasaur #001: Grass/Poison, HP 45, Atk 49, Def 49, SpA 65, SpD 65,
    Spe 45, total 318;
  - Charmander evolves into Charmeleon at level 16, and Charmeleon into
    Charizard at level 36; Eevee has three evolutions;
  - Water is super effective against Fire; Ground has no effect on Flying;
  - Charizard is weak to Rock with a 4× weakness;
  - a numeric filter such as `speed > 100` returns the expected set.
- The existing search, relationship and stage routes return results for
  `PokemonGen1` (at least one route-level test).
- Regenerating the Turtle with the script produces identical bytes.
- `installDist` packages the new resource, and the endpoint works in a local
  smoke run of the built distribution.

## Validation

- Closing gate (Kotlin + packaging): `ktlintCheck detekt test`, then

## Execution log

- 2026-10-05: Card created from the user's request; access and data-era
  decisions recorded above. Implementation is to happen on its own branch.
- 2026-10-05: Implemented on branch `DATA-002-pokemon-gen1-dataset` (worktree
  `../sparql-query-easy-data-002`) from `765f11b`.
  - `scripts/generate-pokemon-dataset.mjs` holds the 151 species and the
    18-type chart. It checks the counts (151 Pokémon with no number gaps;
    51 super effective, 61 not very effective and 8 no-effect matchups) and
    writes `src/main/resources/pokemon_gen1.ttl` (4,740 lines) under
    `http://easyquery.example.org/pokemon#`. `--check` confirms the committed
    bytes match. It uses `owl:Class`/`ObjectProperty`/`DatatypeProperty`
    declarations and `@en` labels, because local search and relationships
    depend on them.
  - Weaknesses come from the chart: `weakTo` covers 2× and 4×,
    `fourTimesWeakTo`, `resistantTo` covers 0.5× and 0.25×, and `immuneTo`.
    Evolution data: `evolvesFrom`/`evolvesInto`, `evolutionStage`,
    `evolutionTrigger` (Level up / Use item / Trade), `evolutionLevel`,
    `evolutionItem` (stones) and `inEvolutionFamily`. Pokédex links:
    `nextInPokedex`/`previousInPokedex`. No Gen 1 evolution in scope uses
    friendship, so it is not modelled.
  - `EndpointContextResolver` takes an optional map of additional built-in
    providers and refuses to replace `CampeonatoBrasileiro2023`.
    `BuiltInGraphEndpointContext` now carries its identifier (defaults to the
    Brazilian ID). `HttpModule` registers `PokemonGen1`.
  - Tests: `PokemonDatasetTest` (resolution and SPARQL oracles: counts,
    Bulbasaur stats, speed/weight filters, evolution lines, chart counts,
    Charizard 4× Rock, Gengar and Magnemite immunities) and
    `PokemonDatasetRoutesTest` (search, relationships and stage through the
    real module).
  - A focused run caught a generator bug ("Leaf Stone" was read as a level,
    producing `NaN`). Fixed it and added a check that rejects unknown
    evolution methods. One route oracle wrongly expected only "Pikachu"; the
    family resource also matches, so the oracle now compares both labels in
    any order.
  - Validation: `./gradlew ktlintCheck detekt test` passed (142 tests).
    `installDist` packages `pokemon_gen1.ttl`. A distribution smoke run on port
    18091 returned health `ok`, `PokemonGen1` search results for "char", and
    unchanged `CampeonatoBrasileiro2023` search. `node
    scripts/generate-pokemon-dataset.mjs --check` passed. No frontend files
    changed, so the browser suite was not required.
  - Docs: Current Contracts, API v1, Workspace Inventory, System Architecture.
  - Limitations: the data tables were written by hand from current-game
    references, not imported from an external source; the oracles
    double-check selected values. Stages and links count only within the 151

    still defaults to `CampeonatoBrasileiro2023`; type `PokemonGen1` to use it.
    The branch is not merged into `main`.
